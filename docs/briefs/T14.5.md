## Rules

**When hooks run.** A hook runs only when `runningSeason(data, state)` is not null (joined and started) and that season's `rules` is not null and defines the hook. Otherwise core behaves exactly as today, consuming the same random numbers. The context is `{ data, season: <the LoadedSeason>, now, rng }`, where `rng` is the action's own Rng, so whatever a hook draws is saved with the state's `rngState` as usual.

**`onTick`** runs once per `tick`, after the whole core tick (orders, events, season, staff), on the state the core tick produced. So it runs on the tick that starts the season and not on the tick that ends it. Its events follow the core tick's. If it returns the state it was given and no events, `dispatch` still keeps the same state object, so an idle tick stays idle.

**`afterAction`** runs after every successful action except `tick`, on the state that action produced, and is given the action and its events. Its events follow the action's. If it rejects, the whole action is rejected and the state is unchanged. It doesn't run after a rejected action.

**`extraSpawns`** is asked on every generator tap that isn't a rare drop, with the tapped generator's item id. Its entries are added to that generator's `spawnTable` and the pick is weighted across both. Staff taps go through `tapGenerator`, so they get the extra spawns too.

**`cooldownMultiplier`** is asked when a tap empties a generator, with the tapped generator's chain id. It multiplies the cooldown along with the event slow and event perks. A cooldown already running isn't changed.

**`orderReward`** is asked for every delivered order, with the order and its reward, before anything is paid. The returned reward is what's paid (coins, stars, XP, reputation) and what `orderDelivered` reports. Season Points and event points are not part of the reward and aren't changed. `deliverOrder` throws if the hook would run but no `rng` was passed (dispatch always passes one).

**Checking what a hook returns.** A bad value is a programming error in the pack and throws, naming the season and the hook:

- `extraSpawns`: every `itemId` must be in `data.items`, every `weight` a finite number above 0.
- `cooldownMultiplier`: a finite number above 0.
- `orderReward`: coins, stars, XP, and reputation if present, each a non-negative integer.
- A hook that throws isn't caught; the error propagates.

**Dev freeze.** When `import.meta.env.DEV` is true (dev builds and Vitest), the state, action, events, order and reward given to a hook are deep-frozen first, so a hook that mutates them throws a TypeError. The context isn't frozen (`data` holds Maps and `rng` is stateful). Production builds skip it.

## Decisions for Scott

1. **An `onTick` rejection throws** rather than rejecting the tick. The store drops a rejected action silently, so a rejected tick would stop new orders, events and staff for as long as the hook kept rejecting. A tick has no player to show a reason to.
2. **Staff taps get the season's extra spawns and cooldown changes** (they use `tapGenerator`). `afterAction` doesn't see staff taps, since they happen inside a tick; `onTick` sees their result.
3. **Rare drops are untouched.** When the rare roll hits, the rare table is used as it is, without extra spawns.
4. **`orderReward` sees every order** (regular, catering, wholesale, seasonal) and the pack chooses by looking at it, e.g. `order.seasonPoints !== undefined` for seasonal orders. The Thanksgiving Feast-order bonus works this way.
5. **The dev freeze freezes the live state in place**, not a copy. A copy would make a hook that returns its state unchanged look like a change every tick. As a side effect, while a season with rules runs in dev, any code that mutates game state throws, which would be a bug anyway. This is the first `import.meta.env` read in `src/core/`.
